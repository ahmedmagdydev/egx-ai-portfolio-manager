# 10 — Testing and Quality

## Purpose

This document defines the testing strategy and quality gates for the EGX portfolio assistant. It covers the test pyramid, golden financial cases, provider contract tests, integration strategy, AI evaluation, Arabic quality, static analysis, coverage expectations, and per-phase quality gates.

## Test pyramid

The test suite has four layers, ordered by frequency of execution:

1. **Unit tests** — deterministic functions in isolation: portfolio accounting, ratios, technical indicators, risk metrics, provider normalization, validation, and utilities.
2. **Contract tests** — provider adapter behavior and repository interfaces against the `MockMarketDataProvider` and in-memory/fake repositories.
3. **Integration tests** — database persistence, API endpoints, migration round-trips, Ollama availability, and RAG retrieval.
4. **End-to-end / AI evaluation tests** — thin UI or API workflows and a fixed bilingual evaluation dataset for the assistant.

Unit and contract tests must be fast and run on every commit. Integration tests may require Docker and Ollama. E2E and AI evaluation tests run in a dedicated job or locally.

## Unit tests

Cover:

- Portfolio calculations: average cost, market value, realized and unrealized P&L, allocation, sector allocation, daily P&L, total P&L.
- Transaction semantics: BUY, SELL, DIVIDEND, DEPOSIT, WITHDRAWAL, FEE; cash impact; partial sells; oversell rejection; same-day ordering; fee handling.
- Financial ratios: P/E, P/B, ROE, ROA, debt-to-equity, profit margin, revenue growth, earnings growth, dividend yield; missing/zero-denominator handling.
- Technical indicators: SMA 20/50/200, RSI 14, MACD, volume; warm-up and insufficient-history behavior.
- Risk calculations: concentration, sector exposure, cash percentage, volatility, maximum drawdown, correlation, Sharpe ratio, optional beta.
- Provider normalization: symbol, timestamp, currency, freshness.
- Validation and error paths.

Use `pytest` with frozen time, parameterized cases, and explicit Decimal fixtures. Avoid `float` in test expectations.

## Golden cases

Create a `tests/golden/` directory with hand-checked input/output files for:

- A known transaction history and its resulting holdings, average cost, and P&L.
- A known OHLCV series and its RSI/SMA/MACD values.
- A known financial statement and its computed ratios.
- A known portfolio and its concentration/risk metrics.

Golden outputs are generated by a trusted reference and verified by inspection. They protect against subtle regressions in financial arithmetic.

## Provider contract tests

The `MarketDataProvider` protocol is tested with a shared suite against:

- `MockMarketDataProvider` (default, offline).
- `ManualCSVProvider` with fixture files.
- Optional fixture replay of a captured public-source sample.

Contract tests verify:

- quote returns correct structure, currency, and freshness;
- historical range respects bounds and ordering;
- invalid/missing symbols raise typed errors;
- malformed source data is rejected;
- stale data is labeled stale;
- idempotent storage of duplicate bars.

## Integration tests

- Database: migrations run forward and backward on a throwaway database, `pgvector` is present, CRUD and constraint behavior work.
- API: FastAPI test client exercises each route, envelope format, freshness metadata, pagination, and error codes.
- Ollama: health endpoint and a small embedding/generation smoke test run against the configured local model.
- RAG: a sanitized document is ingested, chunked, embedded, and retrieved with citation metadata.
- Tool calling: each backend tool is called through its typed interface and returns structured data.

Integration tests use Docker, a disposable test database, and mocked external providers unless explicitly testing Ollama or a validated source in opt-in mode.

## End-to-end tests

Use Playwright or the chosen E2E tool against the local Next.js + FastAPI stack. Focus on:

- Adding a transaction and seeing updated holdings and P&L.
- Viewing a stock quote with source and timestamp.
- Searching documents and seeing citations.
- Starting a chat and confirming Arabic RTL rendering.
- Displaying stale data warnings.

E2E tests run against mock providers and fixture data.

## AI evaluation dataset

Create `evals/ai/` with fixed bilingual cases such as:

- "Analyze COMI for my portfolio."
- "Why did company X earnings decline?"
- "What is my largest concentration risk?"
- "How much of my portfolio is in financial stocks?"
- "حلل COMI بالنسبة لمحفظتي"
- "هل عندي تركيز زائد في قطاع معين؟"

Each case has:

- input prompt;
- expected tool calls (not necessarily exhaustive);
- expected data fields to appear in the response;
- forbidden claims (e.g., invented numbers, trade execution, future guarantees);
- criteria: numerical accuracy, source correctness, tool usage, no hallucination, reasoning quality, Arabic quality.

Evaluation is run against `qwen3.5:9b` as the approved model and recorded with scores and examples.

## Arabic quality checks

- Responses contain grammatically correct Arabic where requested.
- Ticker symbols, numbers, and code remain LTR inside RTL text.
- UI renders correctly with `dir="rtl"` and appropriate fonts.
- Mixed Arabic/English responses preserve meaning and formatting.

## Static analysis and formatting

Backend:

- `ruff` or `flake8` for linting.
- `mypy` or `pyright` for type checking.
- `black` or `ruff format` for formatting.

Frontend:

- ESLint with TypeScript rules.
- Prettier for formatting.
- `tsc --noEmit` for type checking.

Run static analysis in CI and as a pre-commit hook. Fail on warnings unless explicitly annotated.

## Coverage expectations

Target coverage is not a single number. Instead, enforce coverage rules by area:

- 100% of portfolio accounting functions and financial ratio calculations must have unit tests.
- 100% of `MarketDataProvider` contract tests must pass against mock and fixture replay.
- Every API endpoint must have at least one success and one failure integration test.
- Every AI evaluation case must be run and scored before release.

Coverage reports are generated but not used to game metrics. A missing error path is treated as a bug even if the overall number is high.

## Per-phase quality gate

Each phase from the source guide and phase runbooks is complete only when:

1. Unit and contract tests pass.
2. Integration tests for new endpoints and persistence pass.
3. Static analysis passes with no new warnings.
4. Manual demo is completed and notes are recorded.
5. Documentation is updated with any API or schema changes.
6. The phase Definition of Done is signed off.

No later phase may begin before its prerequisites pass their quality gate.

## Test data policy

- Use only synthetic and sanitized fixtures.
- Never commit real portfolio data, private documents, or API keys.
- Fixture files live in `backend/tests/fixtures/` and `frontend/tests/fixtures/`.
- Captured public-source samples must be small, sanitized, and stored with provenance notes.

## Continuous integration

CI must:

1. Install dependencies from lockfiles.
2. Run backend static analysis and unit/contract tests.
3. Run frontend type checks, lint, and unit tests.
4. Run integration tests against a PostgreSQL + pgvector service container and mocked providers.
5. Run AI evaluation in an opt-in job with Ollama available.
6. Generate and archive coverage reports.
7. Block merge on failures.

## Acceptance checklist

- [ ] Unit tests cover all portfolio, ratio, technical, and risk calculations.
- [ ] Golden cases exist for holdings, technical indicators, financial ratios, and risk.
- [ ] Provider contract tests run against mock and fixture replay.
- [ ] Integration tests cover database, API, Ollama health, RAG, and tool calling.
- [ ] E2E tests cover thin portfolio UI and Arabic RTL behavior.
- [ ] AI evaluation dataset is fixed and bilingual.
- [ ] Static analysis and type checking run in CI.
- [ ] Coverage is tracked by critical area, not a single overall percentage.
- [ ] No real portfolio data or secrets are in test fixtures.
